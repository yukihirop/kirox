## 分析サマリー

### 機能スコープと複雑度の概要
Kirox CLIは、GitHubリポジトリからKiro仕様書とステアリングファイルを取得するnpxベースのCLIツールです。現在、**約70%の実装が完了**しており、核となる技術コンポーネントはすでに実装されています。

**実装済み（✅）**:
- プロジェクト基盤（TypeScript、ESM、ビルド環境）
- CLI引数パース・検証（Commander.js）
- 設定管理（.kiroxrc.json、環境変数マージ）
- GitHub API統合（Octokit、並列フェッチ、リトライ、レート制限対応）
- ファイルシステム操作（ディレクトリ作成、上書き確認、パス変換）
- 進捗レポーティング（Chalk色付き出力）

**未実装（⚠️）**:
- メインCLI実行フロー（エントリポイント統合）
- エラーハンドリングシステム（エラー分類・メッセージング）
- 統合テスト・E2Eテスト
- パフォーマンステスト

### 主要な技術的課題
1. **統合の複雑性**: 既存の独立したコンポーネント（CLI、GitHub、FileSystem、Reporting）を一つの実行フローに統合
2. **エラーハンドリングの一貫性**: 各層で発生する異なるエラーを統一的にハンドリングし、ユーザーフレンドリーなメッセージに変換
3. **テスト戦略**: 実際のGitHub APIを使用しない統合テストとE2Eテストの設計

### 全体的な実装アプローチ推奨
**ハイブリッドアプローチ（既存コンポーネント統合 + 新規エラーハンドリング層）**を推奨します。既存の高品質なコンポーネントを活用しつつ、欠けているエラーハンドリングとメインフロー統合に注力します。

**テストカバレッジ**: 20テスト（loader: 10, merger: 10）

### 確立されたパターンと規約

#### アーキテクチャパターン
1. **レイヤー分離**: CLI → GitHub → FileSystem → Reporting の単方向依存
2. **依存性注入**: ProgressReporterなどは呼び出し元から注入
3. **エラー伝播**: 下位層でエラーをthrowし、上位層でキャッチ
4. **非同期パターン**: async/await優先、Promise.allSettled()で部分失敗許容

#### コーディング規約
1. **ファイル命名**: ケバブケース（`progress-reporter.ts`）
2. **型定義ファイル**: 各ディレクトリに`types.ts`を配置
3. **エクスポート**: 名前付きエクスポート優先
4. **インポート順序**: Node.js組み込み → 外部ライブラリ → 内部モジュール（`@/`エイリアス） → 相対パス
5. **TypeScript厳格モード**: `strict: true`、`any`禁止

#### テストパターン
1. **テストフレームワーク**: Vitest
2. **ファイル配置**: `tests/unit/<layer>/<component>.test.ts`
3. **モック**: `vi.mock()`でモジュール全体をモック
4. **環境変数**: `FORCE_COLOR=1`でChalk色付き出力を強制

### 再利用可能なユーティリティとサービス

#### 既に実装済みで再利用可能
1. **`ProgressReporter`**: どのフローでも進捗表示に使用可能
2. **`withRetry()`**: 任意の非同期関数にリトライ機能を追加可能
3. **`Semaphore`**: 並列度制御が必要な箇所で再利用可能
4. **`validateRepository()`/`validateProjectName()`**: 入力検証で再利用
5. **`mergeConfig()`**: 設定マージロジック
6. **`ensureDirectory()`/`writeFile()`**: ファイル書き込み基盤

#### 未実装だが必要
1. **エラーハンドラー**: エラー分類・メッセージ変換の共通ロジック
2. **メイン実行フロー**: 各コンポーネントを統合するオーケストレーター

## 実装戦略オプション

### オプションA: 既存コンポーネントの統合に注力

**アプローチ**:
- `src/index.ts`にメイン実行フローを実装
- 既存の`parser`, `validator`, `fetcher`, `writer`, `progress-reporter`を組み合わせる
- エラーハンドリングは各層でthrowし、`index.ts`でキャッチして処理

**根拠**:
- 既存コンポーネントの品質が高い（190テスト全て成功）
- 新規ファイル作成を最小限に抑えられる
- 実装速度が最も速い

**トレードオフ**:
- ✅ **メリット**:
  - 既存テストを活用できる
  - アーキテクチャの一貫性を保てる
  - 実装工数が少ない（Small: 1-2日）

- ⚠️ **デメリット**:
  - `index.ts`が肥大化する可能性
  - エラーハンドリングが散在しやすい
  - 新規機能追加時の拡張性に課題

**複雑度**: **Small (S)** - 既存パターンの組み合わせのみ

### オプションB: エラーハンドリング層を新規作成

**アプローチ**:
- `src/reporting/error-handler.ts`を新規作成
- エラータイプ分類（VALIDATION, NETWORK, API, FILESYSTEM, UNKNOWN）
- 各エラータイプごとのユーザーフレンドリーなメッセージテンプレート
- `src/cli/entry.ts`を新規作成してメインフローを実装

**根拠**:
- 設計書で推奨されているエラーハンドリング戦略
- エラーメッセージの一貫性を確保
- 将来的な拡張性が高い

**トレードオフ**:
- ✅ **メリット**:
  - エラーハンドリングの一元管理
  - テストしやすい（エラーメッセージの単体テスト）
  - 設計書のアーキテクチャに準拠

- ⚠️ **デメリット**:
  - 新規ファイル作成が必要
  - 既存コンポーネントのエラーをラップする必要
  - 実装工数が増える（Medium: 3-5日）

**複雑度**: **Medium (M)** - 新しいエラーハンドリングパターンの導入

### オプションC: ハイブリッドアプローチ（推奨）

**アプローチ**:
1. `src/reporting/error-handler.ts`を作成（エラー分類・メッセージ変換）
2. `src/index.ts`でメインフロー実装（統合）
3. 既存コンポーネントはそのまま活用

**根拠**:
- オプションAとBの良いところ取り
- エラーハンドリングの一元管理とシンプルな統合を両立
- 段階的実装が可能（エラーハンドラー → メインフロー）

**トレードオフ**:
- ✅ **メリット**:
  - エラーメッセージの一貫性
  - 既存コンポーネントの再利用
  - テストしやすい構造
  - 段階的な実装が可能

- ⚠️ **デメリット**:
  - オプションAより実装工数が増える
  - エラーハンドラーの設計に注意が必要

**複雑度**: **Medium (M)** - エラーハンドリング層の追加 + 統合フロー実装

## 設計フェーズへの推奨事項

### 推奨実装アプローチ
**オプションC（ハイブリッドアプローチ）**を強く推奨します。

**理由**:
1. 既存の高品質なコンポーネント（190テスト、すべて成功）を最大限活用
2. エラーハンドリングの一元管理により、ユーザー体験の一貫性を確保
3. 段階的実装が可能で、リスクを分散できる

### 重要なアーキテクチャ判断が必要な領域

1. **エラーハンドリング戦略**:
   - カスタムエラークラス vs エラーオブジェクトラッピング
   - エラーメッセージテンプレートの管理方法
   - エラーログの詳細度（verboseモード時の動作）

2. **メインフロー実行順序**:
   - 設定読み込み → 引数パース → GitHub取得 → ファイル書き込みの順序
   - 各ステップでのエラーハンドリングポイント
   - 進捗レポーティングのタイミング

3. **統合テスト戦略**:
   - モックGitHub APIサーバーの構築 vs 実際のテストリポジトリ使用
   - E2Eテストの実行環境（Docker? ローカルnpm link?）

### 設計フェーズで更なる調査が必要な領域

1. **統合テストのモック戦略** (優先度: 中):
   - nockライブラリによるHTTPモック vs Octokit専用モック
   - テストデータの管理方法（フィクスチャ）

2. **E2Eテスト実行環境** (優先度: 低):
   - CI/CD環境でのnpx実行テスト
   - クロスプラットフォーム検証（Windows/macOS/Linux）

### 設計フェーズで対処すべき潜在的リスク

1. **統合時の予期しないエラー** (リスク: 中):
   - 各コンポーネントは独立してテスト済みだが、統合時の相互作用は未検証
   - **軽減策**: 統合テストで実際の使用シナリオを網羅的にテスト

2. **パフォーマンス** (リスク: 低):
   - 大量ファイル取得時（50ファイル）のメモリ使用量
   - **軽減策**: Promise.allSettled()とセマフォで並列度制御済み

3. **エラーメッセージの品質** (リスク: 低):
   - ユーザーフレンドリーなメッセージの表現
   - **軽減策**: 要件書のAcceptance Criteriaに明確な例がある
