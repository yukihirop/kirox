# Implementation Plan

## 概要

このタスク計画は、Kirox CLIのインタラクティブモードにおけるプロジェクト選択UIを、二段階プロセスから検索可能な単一ステップUIにアップグレードするための実装手順です。

**重要な技術的制約**: 設計フェーズで`inquirer-ts-checkbox-plus-prompt`パッケージが`@inquirer/prompts` v9+と互換性がないことが判明しました。そのため、タスク1で技術的アプローチを決定し、それに基づいて実装を進めます。

---

- [ ] 1. 技術的アプローチの決定と準備
- [ ] 1.1 `@inquirer/prompts`カスタムプロンプトAPI調査
  - `@inquirer/prompts`の`createPrompt` APIドキュメントを調査
  - `@inquirer/checkbox`プロンプトのソースコードを確認
  - 検索機能を追加する実装難易度を評価
  - カスタムプロンプト実装の例を確認
  - _Requirements: 1.1-1.3（技術選定に影響）_

- [ ] 1.2 技術アプローチの決定
  - Option A（`inquirer`レガシー版にダウングレード）の影響範囲を評価
  - Option B（`@inquirer/prompts`カスタムプロンプト）の実装コストを評価
  - Option C（既存の`search` + `checkbox`改善）の実現可能性を評価
  - メンテナンス性、パフォーマンス、ユーザー体験の観点から最適なアプローチを決定
  - 決定したアプローチをドキュメント化
  - _Requirements: 1.1-1.3, 2.1-2.7（技術選定）_

- [ ] 1.3 必要なパッケージのインストールと環境準備
  - 決定したアプローチに応じて必要なパッケージをインストール
  - TypeScript型定義の利用可能性を確認
  - package.jsonの依存関係を更新
  - `npm install`を実行して正常にインストールされることを確認
  - _Requirements: 1.1-1.3_

- [ ] 2. プロジェクト選択UIの実装（決定したアプローチに応じて実装）
- [ ] 2.1 検索可能なチェックボックスプロンプトの基本機能実装
  - 決定したアプローチに基づいて、検索可能なチェックボックス機能を実装
  - プロジェクト一覧を表示する基本UIを構築
  - リアルタイム検索フィルタリング機能を実装
  - ユーザー入力に基づいてプロジェクトをフィルタリングするロジックを実装（大文字小文字を区別しない部分一致検索）
  - _Requirements: 2.1-2.7_

- [ ] 2.2 プロジェクト表示形式の実装
  - プロジェクトを「サブディレクトリパス/プロジェクト名」形式で表示
  - ルートディレクトリのプロジェクトは「プロジェクト名」のみで表示
  - プロジェクト一覧をアルファベット順にソート（サブディレクトリ優先、同一サブディレクトリ内はプロジェクト名順）
  - `ProjectLocation`型から表示用の選択肢データに変換するロジックを実装
  - _Requirements: 3.1-3.4_

- [ ] 2.3 複数選択とバリデーション機能の実装
  - スペースキーで複数プロジェクトを選択/選択解除する機能を実装
  - Enterキーで選択を確定する機能を実装
  - 最低1つのプロジェクトが選択されていることを検証
  - 選択されたすべてのプロジェクトが同一サブディレクトリに属することを検証
  - バリデーションエラー時に適切なエラーメッセージを表示（選択されたサブディレクトリ一覧を含む）
  - _Requirements: 4.1-4.4_

- [ ] 3. 既存コードの置き換えとリファクタリング
- [ ] 3.1 `promptProjectSelection`関数の実装置き換え
  - `@inquirer/prompts`の`search`と`checkbox`呼び出しを削除
  - 新しい検索可能チェックボックス実装に置き換え
  - `ProjectSelectionResult`インターフェースの返り値型を維持
  - 選択されたプロジェクト名の配列と共通のサブディレクトリパスを返す機能を実装
  - _Requirements: 5.1-5.3_

- [ ] 3.2 二段階UIロジックの削除
  - `__select_multiple__`トリガーロジックを削除
  - 検索プロンプトとチェックボックスプロンプトの切り替えロジックを削除
  - `sourceFunction`内の複雑な状態管理ロジックを削除
  - "No matching projects found"メッセージ処理ロジックを削除（空配列を返すだけで十分）
  - _Requirements: 5.4-5.5_

- [ ] 4. エラーハンドリングの実装と維持
- [ ] 4.1 基本的なエラーハンドリングの実装
  - 選択されたプロジェクトが見つからない場合のエラー処理を実装
  - 有効なプロジェクトが0個選択された場合のエラー処理を実装
  - Ctrl+C中断時の`ExitPromptError`ハンドリングを維持
  - 既存の中断処理フローとの統合を確認
  - _Requirements: 6.1-6.3_

- [ ] 4.2 システムエラーのハンドリング（オプション）
  - プロンプト初期化失敗時のフォールバック処理を実装（実装可能な場合）
  - source関数内の例外処理を実装（エラーログ出力、空配列を返してプロンプト継続）
  - エラーログ出力機能を実装（`logger.error`使用）
  - _Requirements: 6.1-6.3_

- [ ] 5. 既存機能との統合と互換性確認
- [ ] 5.1 `interactive-prompt.ts`との統合確認
  - `promptMissingArguments`関数からの呼び出しが正しく動作することを確認
  - `ProjectSelectionResult`の返り値が期待通りに処理されることを確認
  - Tree API成功後のフローが正しく動作することを確認
  - 既存の呼び出し元コードが変更不要であることを確認
  - _Requirements: 7.1_

- [ ] 5.2 Tree APIフォールバックの維持
  - Tree API失敗時に既存のフォールバックワークフロー（サブディレクトリプロンプト → プロジェクトプロンプト）が動作することを確認
  - フォールバック時のエラーメッセージが適切に表示されることを確認
  - _Requirements: 7.3_

- [ ] 5.3 非インタラクティブモードとの互換性確認
  - 非インタラクティブモード（CLI引数指定）でプロジェクト選択UIが起動しないことを確認
  - CLI引数として渡されたプロジェクト名が正しく処理されることを確認
  - TTY環境でない場合の適切なエラーメッセージ表示を確認
  - _Requirements: 7.4-7.5_

- [ ] 6. ユニットテストの実装と更新
- [ ] 6.1 基本的な選択機能のテスト実装
  - 新しいプロンプト実装が正しいオプションで呼び出されることを検証するテストを実装
  - 選択されたプロジェクトが`ProjectSelectionResult`に正しく変換されることを検証するテストを実装
  - ルートディレクトリプロジェクトの`subdir`が空文字列になることを検証するテストを実装
  - ネストされたプロジェクトの`subdir`が正しく抽出されることを検証するテストを実装
  - _Requirements: 9.1-9.2_

- [ ] 6.2 検索機能のテスト実装
  - 空入力時にすべてのプロジェクトが返されることを検証するテストを実装
  - 大文字小文字を区別しない部分一致検索が動作することを検証するテストを実装
  - サブディレクトリパスに対する検索が動作することを検証するテストを実装
  - フィルタリング結果が0件の場合に空配列が返されることを検証するテストを実装
  - _Requirements: 9.1-9.2_

- [ ] 6.3 バリデーション機能のテスト実装
  - 0個のプロジェクト選択時にエラーメッセージが返されることを検証するテストを実装
  - 同じサブディレクトリのプロジェクト選択時に検証が通過することを検証するテストを実装
  - 異なるサブディレクトリのプロジェクト選択時にエラーメッセージが返されることを検証するテストを実装
  - エラーメッセージにサブディレクトリ一覧が含まれることを検証するテストを実装
  - ルートディレクトリプロジェクトの特別扱いを検証するテストを実装
  - _Requirements: 9.4_

- [ ] 6.4 テストモックの更新
  - 既存のテストファイル(`searchable-project-prompt.test.ts`)のモックを新しい実装に対応させる
  - 新しいプロンプト実装のモック設定を実装
  - source関数のモック実装を追加
  - validate関数のモック実装を追加
  - _Requirements: 9.1_

- [ ] 7. 統合テストとE2Eテストの実行
- [ ] 7.1 統合テストの実行と確認
  - Tree API成功後に新しいプロジェクト選択UIが呼び出されることを確認する統合テストを実行
  - 選択結果が`ParsedArguments`に正しく設定されることを確認する統合テストを実行
  - Tree API失敗時のフォールバックワークフローが動作することを確認する統合テストを実行
  - _Requirements: 9.3_

- [ ] 7.2 E2Eテストの実行と確認
  - リポジトリ入力 → Tree API検索 → プロジェクト選択 → 確認 → 実行の基本フローをテスト
  - 単一プロジェクト選択と複数プロジェクト選択の両方のシナリオをテスト
  - 検索テキスト入力によるフィルタリングとプロジェクト選択のフローをテスト
  - 異なるサブディレクトリのプロジェクト選択時のバリデーションエラーフローをテスト
  - Ctrl+C中断時の終了コード130確認をテスト
  - _Requirements: 9.3_

- [ ] 7.3 テストカバレッジの確認
  - ユニットテストのカバレッジが80%以上であることを確認
  - カバレッジレポートを生成し、未カバー箇所を確認
  - 必要に応じて追加のテストケースを実装
  - _Requirements: 9.2_

- [ ] 8. パフォーマンスとユーザビリティの検証
- [ ] 8.1 パフォーマンステストの実装と実行
  - 100個以上のプロジェクトでリアルタイム検索フィルタリングが1秒以内に完了することを検証するテストを実装
  - フィルタリング結果が100ms以内に表示されることを検証するテストを実装
  - 選択状態の更新が50ms以内に完了することを検証するテストを実装（可能な場合）
  - 1秒間に10回の検索入力（高速タイピング）に対応できることを検証するテストを実装（可能な場合）
  - _Requirements: 8.1-8.2, 8.5_

- [ ] 8.2 ユーザビリティの手動確認
  - プロジェクト一覧がスクロール可能なリストとして正しくレンダリングされることを手動確認
  - 画面サイズに応じて適切に表示されることを手動確認
  - 矢印キーでフォーカスが移動し、ハイライト表示が更新されることを手動確認
  - スペースキーで選択を切り替える動作が直感的であることを手動確認
  - _Requirements: 8.3-8.4_

  - 既存コードとの一貫性を確認（命名規則、コードスタイル）
  - 不要なコメントやデバッグコードが残っていないことを確認
  - エラーハンドリングが適切に実装されていることを確認

- [ ] 9.3 ドキュメント更新（オプション）
