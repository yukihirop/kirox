# Implementation Plan

## タスク概要

本実装計画は、Kirox CLIにサブディレクトリ指定機能を追加し、モノレポ構成のリポジトリから`.kiro`フォルダを取得できるようにする。既存の4層アーキテクチャを維持し、下位互換性を保ちながら段階的に機能を追加する。

## 実装タスク

- [ ] 1. 型定義の拡張とパス正規化・検証ユーティリティの実装
- [x] 1.1 CLI層とConfig層の型定義を拡張
  - ParsedArguments型に`subdir`フィールドを追加
  - KiroxConfig型に`subdir`フィールドを追加
  - MergedConfig型に`subdir`フィールドを追加
  - 既存の型定義との整合性を確保
  - _Requirements: 1.1, 1.2, 2.1, 2.2_

- [x] 1.2 パス正規化機能を実装
  - サブディレクトリパスの先頭・末尾の不要な文字を除去する機能
  - バックスラッシュをスラッシュに変換する機能
  - 連続したスラッシュを単一に正規化する機能
  - 空文字または`.`をrootディレクトリとして扱う機能
  - 正規化されたパス文字列を返す機能
  - _Requirements: 1.4, 1.5, 1.6, 1.7, 1.8, 1.9_

- [x] 1.3 パスセキュリティ検証機能を実装
  - パストラバーサル（`..`）を検出して拒否する機能
  - 絶対パスを検出して拒否する機能
  - 空文字（rootディレクトリ）を有効として扱う機能
  - セキュリティ違反時に明確なエラーメッセージをthrowする機能
  - _Requirements: 3.3, 3.4_

- [x] 1.4 リモートパス構築機能を実装
  - サブディレクトリとプロジェクト名からリモートパスを生成する機能
  - `specs`および`steering`タイプ別のパス構築機能
  - 無効なプロジェクト名を検出してエラーをthrowする機能
  - 空文字サブディレクトリ（root）の場合の適切なパス生成機能
  - _Requirements: 4.1, 4.2, 4.3, 4.4_

- [ ] 2. CLI層のコマンドライン引数パースとバリデーションの拡張
- [x] 2.1 コマンドラインパーサーに`--subdir`オプションを追加
  - `--subdir <path>`ロングオプションの追加
  - `-s <path>`ショートオプションの追加
  - オプション説明「リポジトリのサブディレクトリ配下の.kiroフォルダを指定」の追加
  - パースされた値をParsedArguments型の`subdir`フィールドに格納
  - 既存のオプション定義とのコンフリクトがないことを確認
  - _Requirements: 1.1, 1.2, 7.1, 7.3_

- [x] 2.2 入力バリデーションにサブディレクトリパス検証を追加
  - サブディレクトリパスが指定されている場合のみ検証を実行
  - パス正規化機能を呼び出してパスを正規化
  - パスセキュリティ検証機能を呼び出してセキュリティチェック
  - 検証エラー時にValidationError配列に追加
  - 既存のリポジトリ・プロジェクト名検証に影響を与えないことを確認
  - _Requirements: 3.3, 3.4_

- [ ] 3. Config層の設定ファイル読み込みとマージロジックの拡張
- [x] 3.1 設定ファイルから`subdir`フィールドを読み込む機能を実装
  - `.kiroxrc.json`の`subdir`フィールドを読み込み
  - `subdir`フィールドが存在しない場合はundefinedとして扱う
  - 既存の設定フィールド読み込みに影響を与えないことを確認
  - _Requirements: 2.1_

- [x] 3.2 設定マージロジックに`subdir`の優先順位制御を実装
  - CLIオプションの`subdir`が指定されている場合はそれを優先
  - CLIオプションが未指定の場合は設定ファイルの`subdir`を使用
  - 空文字が指定された場合はrootディレクトリとして扱う
  - 既存の設定マージパターン（CLI > Config > Default）と一貫性を保つ
  - _Requirements: 2.2, 2.3, 2.4, 2.5_

- [ ] 4. CLIエントリポイントでのパス構築ロジックの統合
- [x] 4.1 CLIエントリポイントでマージされた設定からサブディレクトリを取得

  - 取得したサブディレクトリパスが正規化済みであることを前提とする
  - _Requirements: 2.1, 2.2_

- [x] 4.2 リモートパス構築ロジックを新しい関数に移行

  - 既存の`getSteeringDirectoryPath`呼び出しを`buildRemotePath`に置き換え
  - サブディレクトリ、プロジェクト名、タイプ（specs/steering）を渡して構築
  - 構築されたリモートパスをGitHub APIに渡す

## 実装順序の理由

1. **タスク1**: 基盤となる型定義とユーティリティ関数を最初に実装することで、後続のタスクで使用可能にする
2. **タスク2-3**: CLI層とConfig層の拡張により、ユーザー入力と設定の取り込みを完成させる
3. **タスク4-5**: CLIエントリポイントとReporting層の統合により、エンドツーエンドの機能を完成させる
4. **タスク6-7**: エラーハンドリングと下位互換性の確保により、堅牢性を向上させる
5. **タスク8-10**: テストの実装により、品質を保証する
6. **タスク11**: ドキュメントの更新により、ユーザー体験を完成させる
